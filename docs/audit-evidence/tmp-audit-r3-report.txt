THE STOPPING RULE
============================================================
The bar you proposed:

  An item is certified when an audit round finds no defect of a CLASS not
  already fixed. Variants inside an already-closed class get logged as
  known and accepted.

It is too low if YOU classify the leftover.

These two item-15 fails are exactly what that sentence would let you call
variants: they are adjacent, they are the same class, they are not repeats
of the four gates you just wrote. If adjacency is enough to accept them,
we certify a class that is still open, and we will be here again.

A class is closed when the stated positive rule already DECIDES the new
attack — refuses it, or allows it as a written exception. A variant is a
new spelling of something the rule already decides. A hole is an attack
the rule does not decide, or decides wrongly.

"Index supplies its own tsconfig" decides these wrongly (it supplied one;
the guard passed). They are not variants. They are the class still open.

What I would use:

1. The rule is stated positively. (You just started doing this. Keep it.)
2. I classify each leftover, not you. You may argue; you may not decide.
3. VARIANT = the stated rule already refuses this, or already allows it
   as a named exception (hatch, node_modules, noCheck-in-the-index).
4. HOLE = the stated rule does not decide this, or decides it wrongly.
5. Certify when a round produces no hole and no new class.
6. Known-accepted leftovers are written as consequences of the rule
   ("tsc trusts the staged noCheck flag"), never as "adjacent, so drop it."

That is a higher bar than "no new class." It is not an infinite bar. Item
13 met it this round. Item 10 met it this round. Item 18 met it this
round. Item 15 did not, and the reason is the same habit you already
named: the rule is still an enumeration of guard lookups, not a statement
of what the compiler is allowed to see.
